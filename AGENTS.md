# Settlement — инструкции для Codex

## Архитектура проекта

- Сервер: Clojure, TCP, STM.
- Клиент: Java Swing.
- Автономный бот: SWI-Prolog, DCG, динамические факты, A*.
- Графика: 2.5D Pixel Art.
- Человек — синяя команда, Prolog-бот — красная.

## Правила разработки

- Не изменять утверждённые механики без согласования.
- Сохранять обратную совместимость.
- Не переписывать работающий код без необходимости.
- Не изменять посторонние файлы.
- Не удалять ресурсы без проверки зависимостей и резервного копирования.
- Не выполнять git commit и git push без разрешения пользователя.

## Экономия ресурсов Codex

- Изучать только файлы, необходимые для текущей задачи.
- Не проводить повторный анализ всего проекта.
- Использовать существующие генераторы, текстуры и кэш.
- Не перегенерировать неизменённые ресурсы.
- Разделять масштабные задачи на небольшие этапы.
- Не повторять успешные проверки без необходимости.
- Не выполнять бесконечные циклы улучшения.
- Предоставлять краткие отчёты.
- При достижении границы текущего этапа останавливаться.

## Тестирование

На промежуточных этапах:

- Запускать профильные тесты.
- Создавать 2–4 необходимых скриншота.
- Проверять изменённую функциональность.
- Выполнять git diff --check.

Перед утверждением полноценной версии:

- Запускать все тесты Clojure, Prolog и Python.
- Проверять генерацию мира на 30 seed.
- Проверять TCP и серверные коллизии.
- Проверять Prolog A* и автономный матч.
- Проверять перезапуск игры.
- Измерять производительность при 1280×720, 1920×1080 и 2560×1440.

## Требования к графике

- Единый высокодетализированный пиксельный стиль.
- Естественная геометрия рельефа.
- Корректное освещение и тени.
- Отсутствие визуальных артефактов.
- Корректное перекрытие персонажей.
- Соответствие визуальной и логической геометрии.
- Целевой p95 отрисовки не более 16,67 мс после прогрева.
- Обязательная визуальная проверка в Swing.
- Не включать экспериментальные версии по умолчанию без утверждения пользователя.

## Контекст проекта

Перед началом работы изучать docs/PROJECT_STATE.md, если файл существует.

После завершения каждого этапа обновлять его:

- Текущая версия.
- Выполненные задачи.
- Изменённые компоненты.
- Результаты проверок.
- Известные проблемы.
- Следующий этап.

Экономия ресурсов не должна снижать качество графики и надёжность игры.
